# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Feedscape for Facebook" — a Manifest V3 Chrome/Edge extension. No build step, no bundler, no package manager, no tests — plain JS/HTML/CSS loaded directly by the browser. Hides distracting Facebook feed/sidebar sections (Birthdays, Contacts, Shortcuts, Stories, Reels, Videos, Sponsored, People You May Know, posts from unfollowed Pages/Groups) and lets the user tag or hide specific people's posts, with a colored-badge tagging system and a light/dark theme toggle in the settings UI. Not published to the Chrome Web Store — installed as an unpacked extension (see `README.md` for the user-facing install/usage guide; this file is dev-facing).

## Load / test in browser

There is no CLI build or test suite. To verify a change:
1. Open `chrome://extensions` (or `edge://extensions`).
2. Enable Developer Mode, "Load unpacked", select this folder.
3. Open/refresh a Facebook tab — content script runs at `document_start` (see note below on why).
4. After editing `content.js`/`content.css`, click the reload icon on the extension card, then refresh the Facebook tab.
5. After editing `popup.*`/`options.*`/`settings.js`, just reopen the popup or options page (no extension reload needed unless `manifest.json` changed).

Manual verification is the only verification path here — there's no automated test harness. When making a change, state what you clicked through in Facebook to confirm it.

## Architecture

Two independent pieces, connected only through `chrome.storage.local`:

- **Settings UI** — `popup.html` (compact popup) and `options.html` (full page, opened via `chrome.runtime.openOptionsPage()` — `manifest.json`'s `options_ui.open_in_tab: true`). Both load the same `settings.js`, which reads/writes `chrome.storage.local` directly; the two HTML files just need matching element IDs (checkboxes by id, `predefinedTagText`/`predefinedTagColor`/`addPredefinedTag`/`predefinedTagChips`, `tagName`/`tagValue`(a `<select>`)/`addTag`/`tagChips`, `hiddenPeople` textarea, `save`/`status`, `themeToggle`). `popup.html` also has an `openOptions` button `settings.js` wires to `chrome.runtime.openOptionsPage()`; `options.html` has no such button since it *is* the full page. There is no `popup.js` — it was folded into `settings.js` when the options page was added, so both surfaces share one implementation.
  - Tag color is a property of the **tag text**, not of any one person: `tags` is `{ "Full Name": "tag text" }` (plain string) and `tagColors` is `{ "tag text": "#rrggbb" }` — one color per distinct tag, shared by everyone tagged with it. The "Predefined tags" section manages `tagColors` directly (its own add/remove chip UI); the "Tag people" section only *assigns* an existing tag to a name via a `<select>` populated from `tagColors`' keys — it has no color picker of its own. Removing a predefined tag doesn't cascade into `tags` (people keep the text; the badge just falls back to the default color in the feed until re-tagged from the palette) — don't "fix" this into a cascading delete, it was a deliberate choice to avoid silently un-tagging people.
  - A brief earlier version stored `tags[name]` as `{ text, color }` (color per person, not per tag). Both `settings.js` and `content.js` still migrate that shape transparently on read (see `getPersonTagText`/the `DOMContentLoaded` handler) — don't remove that without confirming no installs still have the old shape.
  - `hiddenPeople` stays a plain textarea, one name per line → string array on save.
  - Theme (`light`/`dark`) is stored under its own `theme` key, read/written independently of the main Save button (feels instant, like any app's dark-mode switch) — don't fold it into the `DEFAULTS`/`CHECKBOX_IDS`/Save flow. `settings.js` paints a same-tick best-guess from `prefers-color-scheme` before `DOMContentLoaded` even fires (avoids a flash), then corrects from storage once it responds.
- **`content.js`** — injected into every `facebook.com` page. Loads settings from storage, applies DOM hiding/tagging, and re-applies on every DOM mutation via a throttled `MutationObserver`, plus a 1s `setInterval` safety-net poll (Facebook's SPA re-renders can otherwise leave a widget unhidden until some unrelated mutation happens to trigger a recheck — see comment at the bottom of the file). Also listens for `chrome.storage.onChanged` so changes in either settings UI take effect without a page refresh.
- **`content.css`** — `.fbcustom-hidden` (display:none), `.fbcustom-tag` (colored badge, color driven by a `--tag-color` custom property set per-element in JS), `.fbcustom-tag-highlight` (tints the whole name area, not just the badge, when tagged), `.fbcustom-tag-btn` (small "+"/"✎" button next to an author name or profile header), and `.fbcustom-tag-editor*` (a small on-page popover — text input + native color picker — that opens when the button is clicked; replaces `window.prompt()`, which can't offer a color picker).

Both `settings.js` and `content.js` define their own copy of `DEFAULTS` and their own `DEFAULT_TAG_COLOR`/tag-normalization helpers — keep them in sync when adding a setting (add to both `DEFAULTS` objects, add a checkbox with matching id to *both* `popup.html` and `options.html` + the id to `CHECKBOX_IDS` in `settings.js`, add the read/apply logic in `content.js`'s `processPage()`).

### DOM-matching strategy (content.js)

Facebook has no stable class names or public API, so all matching is heuristic, by design:
- `findExactTextElements(list)` finds leaf elements (no children) whose exact trimmed text matches a known string (e.g. "Birthdays", "Sponsored"). Leaf-only avoids matching a wrapper div that merely *contains* the word. Doesn't work for headings whose text is split across a nested icon + zero-width-space span (e.g. "People You May Know") — those need a different anchor (see `hidePeopleYouMayKnow`).
- `getAuthorNameLinks()` — **important, easy to get wrong**: it searches the *whole document* (`h2/h3/h4 a`, `strong a`), not scoped to any one post. An earlier version scoped this per-`[role="article"]`, which silently matched nothing, because — confirmed against live markup — a post's `[role="article"]` wraps only its message/media/actions area, **not** its header row. The author-name link (and, separately, the "Follow" button FB shows on unfollowed sources) live in that header row, outside any `[role="article"]`. This one wrong assumption was the root cause of several bugs in one session (the feed tag button never appearing, hide-by-name never firing, unfollowed-post hiding never firing) before it was traced and fixed — don't reintroduce per-article scoping for anything that needs to find a post's header content.
- `hideArticleAncestor(startEl, markerAttr)` — the "hide the whole post starting from any element inside it" primitive, used for sponsored-post hiding, unfollowed-post hiding, and hide-by-name. Three tiers, each falling back to the next only if the previous finds nothing, so it can't guess broad and hide multiple posts:
  1. `startEl.closest('[role="article"]')` — fast path for elements already inside the article (e.g. a "Sponsored" label in the message body).
  2. Walk up from `startEl` looking for the smallest ancestor containing **exactly one** `[role="article"]` descendant — handles header-zone elements (name link, "Follow" button) by finding the true post-card boundary from outside the article. Bails if it ever sees more than one article before finding exactly one.
  3. `startEl.closest('[data-pagelet]')` — some ad units have *neither* `[role="article"]` nor `[role="feed"]` anywhere in their ancestry (confirmed live); `data-pagelet` scopes to one feed story/widget precisely (e.g. `"FeedUnit_5"`) and is the last resort.
- `hideTopLevelChildOfAncestor(startEl, ancestor, markerAttr)` walks up from a matched element to the nearest child of a given ancestor and hides that whole child — hides "the widget" without knowing FB's generated class names. Silently no-ops if `ancestor` is null, so a wrong/missing ancestor selector fails quietly rather than throwing — worth grepping for stray `null` ancestors if a hide isn't taking effect.
- `hideEnclosingCard(startEl, markerAttr)` hides the nearest ancestor carrying the inline `style="border-radius: ...var(--card-corner-radius)..."` used by Stories/Reels/People-You-May-Know card wrappers — hides the card's title+menu along with its tray, not just the tray. **Caveat**: that style isn't unique to these widgets; FB's design system reuses it broadly, so on some pages `closest()` can walk past the intended small card and match something far larger. Guarded with `!card.querySelector('[role="article"]')` (never hide a card that contains an actual post) after this exact failure mode broke post loading on profile pages — don't remove that guard without a replacement safety check.
- Every hide/tag operation sets a `data-fbcustom-*` marker attribute so the mutation observer doesn't reprocess the same element repeatedly.
- `HEADING_MATCHERS` text is English-only. Facebook UI language is per-account; if you need another language, add more strings to the matcher arrays (comment in the file explains this).

When Facebook changes its markup, matching by heading text, `aria-label`, a semantic attribute (`role`, `data-pagelet`, `data-ad-rendering-role`), or a stable inline style/CSS-variable reference tends to survive redesigns better than positional/class selectors — keep new heuristics in that style. Prefer anchoring from an element you can already reliably match over guessing at ancestor roles/scoping — and if a feature silently matches nothing with no console error, suspect a wrong scoping assumption (see `getAuthorNameLinks` above) before suspecting the text/attribute matcher itself.
